# AgentOS Release Hardening

Canonical path: `docs/release-hardening.md`.

## Target Conclusion

Release hardening does not add runtime capability. It turns the Phase 6
`0.3.0a1` cutover into a reviewable and publishable SDK release candidate by
requiring concrete, revision-bound evidence.

The SDK-owned release evidence is:

- public API audit
- stable API and experimental API inventory
- machine-readable public API inventory at `docs/public-api-inventory.json`
- API stability classification
- machine-readable release evidence template at `docs/release-evidence.example.json`
- generated local release candidate evidence at `docs/release-evidence.json`
- committed release evidence generator at `scripts/generate_release_evidence.py`
- release evidence validator:
  `validate_release_evidence_manifest`,
  `validate_release_candidate_evidence_manifest`,
  `ReleaseEvidenceValidationReport`, and
  `RELEASE_EVIDENCE_REQUIRED_GATES`
- migration index
- README / quickstart / examples alignment
- `CHANGELOG.md`
- full test suite evidence
- diff/commit hygiene
- boundary scan evidence for the single async `QueryLoop` and `agentos.sync`

AgentOS does not run CI/CD, signing, publishing, deployment approval. Those are
deployment-owned release operations. The SDK owns the evidence format,
documentation, reference commands, release gate checklist, and
machine-readable release evidence manifests. The example manifest is
non-certifying SDK evidence and a schema template. The actual release candidate
evidence manifest is generated by the committed
`scripts/generate_release_evidence.py` entry point, ignored by git, and points
at the immutable source commit that was tested and reviewed. Pending or unknown
gates are intentionally not treated as passed. Neither manifest is a production
certification, deployment approval, signing record, or publishing record.

The release evidence validator is an SDK-owned machine-readable gate over
existing evidence. `validate_release_evidence_manifest` checks that
`RELEASE_EVIDENCE_REQUIRED_GATES` are present and passed, that pending or
failed independent review blocks release-candidate promotion, and that
`ReleaseEvidenceValidationReport` redacts secret-like values from validation
payloads. The release-candidate gate uses
`validate_release_candidate_evidence_manifest`, which requires expected branch,
commit, and version identity before accepting a manifest. This keeps flexible
unit validation separate from the actual release gate path, where the manifest
must be bound to the source revision under review. It does not execute the test
suite, run backend probes, sign artifacts, publish packages, or approve
deployment.

## Release Hardening Gate

A Phase 6 release candidate passes the release hardening gate only when every
item below has evidence in the branch:

| Gate item | Evidence |
|-----------|----------|
| Release scope | `docs/release-scope.md` describes the `0.3.0a1` breaking alpha. |
| API stability | `docs/api-stability.md` classifies stable API and experimental API surfaces. |
| Public API inventory | `docs/public-api-inventory.json` records selected public exports, stability classes, and current signatures. |
| Release evidence template | `docs/release-evidence.example.json` records the machine-readable schema with placeholders and non-certifying SDK evidence. |
| Actual release evidence | Generated `docs/release-evidence.json` records actual release candidate evidence, current gate status, commands, evidence refs, and verification timestamps without placeholders. It is intentionally ignored by git so it can point at the tested commit instead of self-referencing its own committed hash. |
| Release evidence generator | `scripts/generate_release_evidence.py` reproduces the ignored manifest from committed source, source identity, and explicitly supplied gate results. |
| Release evidence validator | `src/agentos/release.py` validates the manifest, fails closed on missing/pending/failed required gates, applies secret-like value redaction, and exposes `validate_release_candidate_evidence_manifest` for the release gate path that requires expected branch, commit, and version identity. |
| Public API audit | `uv run pytest tests/architecture/test_public_api.py -q` passes. |
| Migrations | `docs/migrations/README.md` lists schema/data migrations and migration ownership. |
| README alignment | `README.md` links release scope, readiness, API stability, migration index, quickstart, and examples. |
| Quickstart alignment | `docs/quickstart.md` names supported release shapes and links release gates. |
| Examples alignment | `src/agentos/examples/` includes runnable examples with `if __name__ == "__main__"`. |
| Changelog | `CHANGELOG.md` records the Phase 6 cutover and migration boundary. |
| Tests | `uv run pytest -q` provides full test suite evidence. |
| Diff hygiene | `git diff --check` provides whitespace evidence. |
| Runtime boundary | Search confirms planner/A2A/team/worker/state-plane/readiness/sandbox/release-hardening concepts are not moved into the single async `QueryLoop`; `agentos.sync` remains an adapter only. |

## Reference Commands

Ordinary unit tests do not read the ignored local
`docs/release-evidence.json` candidate artifact. Run the normal contract tests
without enabling local candidate validation:

```powershell
& (Resolve-Path '.\.venv\Scripts\python.exe') -m pytest tests/test_release_evidence.py tests/test_release_evidence_local.py tests/test_release_evidence_cli.py -q
```

To validate the current worktree's local candidate artifact through pytest,
enable the explicit gate first:

```powershell
$env:AGENTOS_VALIDATE_LOCAL_RELEASE_EVIDENCE='1'
& (Resolve-Path '.\.venv\Scripts\python.exe') -m pytest tests/test_release_evidence_local.py -q
```

Release automation must use the non-skippable validator CLI with explicit
candidate identity:

```powershell
& (Resolve-Path '.\.venv\Scripts\python.exe') scripts/validate_release_evidence.py --manifest docs/release-evidence.json --branch <current-branch> --commit <current-commit> --version <pyproject-version>
```

Use these commands as release candidate evidence:

```bash
uv run python scripts/generate_release_evidence.py --output docs/release-evidence.json --branch <current-branch> --commit <current-commit> --version <pyproject-version> --independent-review-status pending
uv run pytest tests/docs/test_production_hardening_docs.py tests/docs/test_production_readiness_docs.py tests/docs/test_objective_coverage_audit_docs.py -q
uv run pytest tests/test_release_evidence.py tests/test_release_evidence_local.py tests/test_release_evidence_cli.py -q
python -m json.tool docs/release-evidence.example.json
python -m json.tool docs/release-evidence.json
python -m json.tool docs/public-api-inventory.json
uv run pytest tests/architecture/test_public_api.py -q
uv run python -m compileall -q src tests
git diff --check
rg -n "TaskStore|RunStore|SessionProvider|sqlite|postgres|redis|Worker|Daemon|from agentos.runtime import Agent" src/agentos/transports
uv run pytest -q
```

The boundary scan should produce no matches in the single async QueryLoop or
the `agentos.sync` adapter.

When validating actual release candidate evidence, call
`validate_release_candidate_evidence_manifest` with the expected branch, commit,
and version from the release run. The release gate requires expected branch,
commit, and version identity; callers that omit or pass placeholder identity
must fail closed even if every gate payload otherwise looks valid.

## Release Boundary

The `0.3.0a1` alpha supports Local, Durable, and Distributed profiles over one
async execution kernel, plus typed context, Artifact, transport, team, planner,
side-effect, readiness, and release-evidence boundaries.

Sandbox / Docker / E2B / microVM / enterprise runner adapter work is a
non-blocking future adapter. The release does not promise physical isolation
for untrusted code execution. Production specs must choose one sandbox posture:
`trusted tools only`, `deployment-owned isolation`, or `future adapter`.

## SDK-Owned And Deployment-Owned

SDK-owned release evidence:

- protocols and public API exports
- machine-readable public API inventory and signature evidence
- readiness and audit evidence shape
- machine-readable release evidence manifest
- release evidence validator and validation report
- reference state plane composition
- reference live backend probe invocation plans
- migration documentation index
- stable/experimental API classification
- docs, quickstart, examples, and changelog alignment

Deployment-owned release operations:

- CI/CD execution and approval policy
- artifact signing and publishing
- production deployment approval
- Kubernetes, systemd, autoscaling, tenant directory, and secret distribution
- backend credentials, migration execution, alerting, runbooks, rollout, and rollback
- physical isolation for untrusted code execution
